What the conversion does

seagliderOG1 converts Seaglider basestation files (pSSSDDDD*.nc) into OG1 format, the OceanGliders community format for glider data exchange. This page describes what changes between the input and the output.

Overview

Seaglider data is produced in a basestation format that varies between deployments and has changed over time. OG1 is a single, CF-compliant layout for sharing glider data.

Inputs

  • the per-dive basestation files of one mission (pSSSDDDD_YYYYMMDD.nc, one file per dive-climb cycle);

  • a mission.yaml — the per-deployment metadata you supply (platform, contributors, institutions, raw-data directory, dive range, mode; see Configuration);

  • the packaged OG1 mappings and vocabularies, the same for every mission (see Packaged defaults and your local tables).

Outputs

  • one OG1 file per mission, all dive-climb cycles concatenated onto a single measurement axis (sg_data_point becomes N_MEASUREMENTS);

  • a conversion record <id>_conversion.json beside it (what was renamed, merged and dropped, and each variable’s per-dive presence);

  • optionally an HTML conversion page (see The conversion page).

Overall action — concatenate the dives onto one measurement axis; rename variables to OG1, attach CF and OG1 attributes, and convert units; add platform, sensor, contributor and institution metadata from the mission.yaml; and add GPS fixes, dive and profile numbering, and dive phase. A basestation variable OG1 does not name is passed through under its own name.

The steps

seagliderOG1.convert turns the dive files of one mission into one OG1 dataset. In order:

  1. Plan the merge. Read every dive file’s dimensions and decide which merge onto the measurement axis (sg_data_point becomes N_MEASUREMENTS) and which are carried as scalars. Build the basestation → OG1 name mapping once, across all files, so a variable present in only some dives gets the same name everywhere. Page: Dimensions; Reconciliation.

  2. Per dive file:

    • merge that file’s dimensions onto the measurement axis;

    • append the GPS fixes as extra rows (LATITUDE_GPS, LONGITUDE_GPS, TIME_GPS);

    • add DIVE_NUMBER, PROFILE_NUMBER and PHASE;

    • apply the OG1 vocabulary: rename, attach the OG1 attributes, convert units, mark the coordinates, encode time. A variable with no OG1 name keeps its basestation name.

    Page: Derived variables; Variables.

  3. Concatenate the dives on N_MEASUREMENTS and sort by TIME. Page: Before → after (samples on the shared axis).

  4. Sensors. Gather each instrument’s record from the calibration comments, apply the sensors: corrections from the mission file, write one SENSOR_* variable per instrument and point each measured variable’s sensor attribute at it. Mission file: sensors:. Page: Sensors named by OG1.

  5. Scalars. Collect the per-dive parameters (log_*, sg_cal_*, gc_*); a value constant across the mission is stored as a scalar, one that varies is stored per dive. Page: Scalar parameters.

  6. Identity and metadata. Resolve the platform fields (mission file over the first dive file’s attributes), add TRAJECTORY, apply the global attributes from the three sections, the contributor and institution records, the coverage bounds computed from the data, and the conversion record. Mission file: platform:, identity_and_discovery:, rights_and_access:, provenance_and_processing:, contributors:, institutions:. Page: mission.yaml against the data; Global attributes.

Steps 1 and 3–6 run once per mission; step 2 runs once per dive file. Each Page: note names the section of the The conversion page that shows that step’s result.

What changes

The steps above apply these transformations; each is detailed below.

Variable names

Variable names are mapped to OG1 (full mapping in OG1_variable_names.yaml):

Basestation   OG1
----------------------------
latitude      LATITUDE
longitude     LONGITUDE
ctd_time      TIME
gps_lat       LATITUDE_GPS
gps_lon       LONGITUDE_GPS
eng_pitchAng  PITCH
eng_rollAng   ROLL
ctd_depth     DEPTH

Units

  • Units are converted to the OG1 preferred units where a mapping exists (for example cm/s to m/s); the mappings are in vocabularies.py.

  • Variables carry standard_name, long_name and units.

  • Controlled vocabularies come from NERC.

GPS data

GPS fixes are appended to the dataset as extra rows along N_MEASUREMENTS (increasing its length), not interpolated onto the measurement times:

  • LATITUDE_GPS, LONGITUDE_GPS and TIME_GPS hold the fix values, non-NaN only at the appended GPS rows;

  • the dataset is sorted by TIME after the fixes are added.

Sensors, global attributes and QC

  • Sensors: sensor information and calibration coefficients are catalogued from the basestation attributes and written as OG1 sensor variables.

  • Global attributes: CF and OG1 global attributes from config/OG1_global_attributes.yaml and the mission configuration.

  • QC variables: where the basestation input carries a <name>_qc flag, it is carried through as the OG1 <NAME>_QC companion of the kept variable; variables with no input flag do not gain one (convert.py).

Extended variables

Beyond the core OG1 variables, the output preserves:

  • flight-model velocities (vertical and horizontal) from the glider flight model;

  • engineering variables describing glider state;

  • derived oceanographic variables where present in the input.

Variables that differ between dives

The basestation files of one mission need not carry the same variables: a sensor switched on part-way through, or present but off, makes the files disagree. The converter works from the union of the variables, so the OG1 file has one variable where the inputs had it on some dives and not others, and cannot say which dives that was.

seagliderOG1.process (and the process CLI) records this in <id>_conversion.json beside the OG1 file. For each basestation variable it gives the runs of dives it is present in (the variable exists in the file) and valid in (present, with at least one non-missing value). The conversion record also lists the input files, records the dives, platform and institutions values the conversion was given (not for a draft) and the basestation institution global’s registry match, and carries the file’s id, tracking_id and SHA-256; the conversion-record reader reads it back and ignores a conversion record whose id or tracking_id differs from the file’s (seagliderOG1 report also checks the SHA-256).

The conversion page groups the variables into patterns — every dive, from dive k, until dive k, dive k only, dives a–b, sporadic — and shows each as a strip over the dives. On the bundled demo_sg005 sample (dives 1–5), 338 variables are on every dive, the four depth-averaged currents are present on every dive but have values from dive 2, and log_ALTIM_BOTTOM_PING is on dive 4 only.

Nothing about this is added to the OG1 file.

Checking the output

The validate verb checks the mission configuration before conversion: known and required keys, that raw_dir is reachable and holds basestation files, the dive range, the required platform fields, and that the contributor and institution records include at least one PI and one Operator. During conversion the input coordinates are checked. Neither step runs an OG1 compliance check on the output file.

Output files target:

  • OG1 Format Specification

  • CF Conventions (version 1.10)

  • ACDD Conventions

The output carries featureType: trajectory (config/OG1_global_attributes.yaml).

Two results of the OG1 checker (ioos/cc-plugin-og, compliance-checker --test og:1.0) are expected on every file this package writes:

  • Variable names should be capitalized — a basestation variable with no OG1 name keeps its basestation spelling (log_D_TGT, sg_cal_calibcomm, sbe41), so its name shows at a glance that it is not an OG1 variable. The OG1 manual calls upper-case variable names “the OG1 convention” (in its sensor-variable section); keeping the basestation spelling is a deliberate departure from it. Variables renamed to an OG1 name are upper case; a variable passed through carries original_name equal to its name.

  • Global attribute comment is missing — when provenance_and_processing.comment in mission.yaml is null. The OG1 manual lists comment as suggested (cc-plugin-og 0.1.2 checks it as mandatory), so the converter writes no default text; set it to add one.

Any other checker finding is a converter problem. To run the checker:

$ pip install cc-plugin-og
$ compliance-checker --test og:1.0 <output_dir>/<id>.nc

For the data themselves, use glidertest.
